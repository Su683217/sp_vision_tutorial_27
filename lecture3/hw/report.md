## 1. 图像生命周期与所有权

解释本项目中图像源为什么会复用缓冲区，以及 `cv::Mat` 的普通复制对底层像素数据
意味着什么。说明你的修改让一个 `Frame` 在进入队列后拥有什么，并解释为何后续读取
不会再改变它。

**为什么复用缓冲区。** `ImageSequenceSource` 模拟的是真实相机驱动：相机为了速度，
会预先分配好一块固定大小的内存，每取一帧就把新像素写进**同一块**内存，而不是每帧重新
申请。代码里对应的是 `raw.copyTo(buffer_)`：当 `buffer_` 的尺寸和类型不变时，`copyTo`
不会重新分配内存，而是直接覆盖 `buffer_` 原来那块像素。

**`cv::Mat` 普通复制的含义。** `cv::Mat` 由两部分组成：一个很小的头部（行列数、类型、
指向像素的 `data` 指针和引用计数），以及单独存放在堆上的像素数据。`frame.image = buffer_`
这样的普通赋值只复制头部、把引用计数加一，`frame.image` 和 `buffer_` 的 `data` 指向的
是同一块像素，也就是浅拷贝。

原实现正是这样做的，所以 producer 放进队列的每一帧都指向 `buffer_` 的像素。producer 读
下一张图时会覆盖这块内存，而 worker 还没处理的旧帧也跟着被改掉了，校验值对不上，运行
结果是 20 帧里 19 帧被判定为损坏。

**修改后 `Frame` 拥有什么。** 改为 `frame.image = buffer_.clone();`。`clone()` 是深拷贝，
会新分配一块内存并复制全部像素。因此每个 `Frame` 进入队列时，持有的是一份**只属于它自己**
的像素数据，这块数据不再和 `buffer_` 共享。之后 `next()` 再怎么覆盖 `buffer_`，改的也只是
`buffer_` 自己那块内存，已经入队的帧不受影响。这块像素的生命周期跟着 `Frame` 走：随
`Frame` 被移入队列、被 worker 取出，最后一个引用它的 `cv::Mat` 析构时自动释放（RAII）。

另外，producer 入队时改成了 `queue_.push(std::move(frame))`。`frame` 在下一轮循环里会被
`next()` 整体覆盖，原来的内容不再需要，所以用 `std::move` 把资源直接转交给队列，避免多复制
一次。两者分工不同：`clone()` 解决"要不要生成独立的数据"，`std::move` 解决"已有的数据交给谁
接管"。帧之间互不干扰是由 `clone()` 保证的，`std::move` 只是减少不必要的复制。

## 2. 并发处理与恰好一次

结合 `BlockingQueue` 的 `push`、`pop` 和 `close` 行为，解释多个 worker 如何分工。
为什么你的实现既不会漏掉已经入队的帧，也不会重复处理同一帧？输入耗尽时，正在等待
以及仍在处理数据的 worker 分别会怎样？

**队列的三个操作。**

- `push`：加锁后把元素放到队尾，然后 `notify_one` 唤醒一个等待的 worker。如果队列已经
  关闭，新元素会被直接丢弃。
- `pop`：加锁后等待条件"已关闭 **或** 队列非空"。满足后，如果队列非空就取出队首并删除，
  返回 `true`；只有在**已关闭且队列为空**时才返回 `false`。
- `close`：加锁设置关闭标志，然后 `notify_all` 唤醒所有在等待的 worker。

**多个 worker 如何分工。** 所有 worker 都在循环里调用同一个队列的 `pop`，谁先抢到锁谁就
取走队首那一帧。具体哪个 worker 处理哪一帧取决于线程调度，但"检查队列、取出队首、删除
队首"这三步都在同一把锁里完成。

**为什么不会重复。** 由于取出和删除是在同一次加锁中完成的，一帧一旦被某个 worker 取走就
已经从队列里删除了，其他 worker 不可能再取到它。每帧的 `id` 唯一，输出文件也按 `id` 命名，
所以每帧只会被处理、保存一次。

**为什么不会漏。** producer 是在同一个线程里先把全部帧 `push` 完，再调用 `close()`，所以
关闭之前所有帧都已经在队列里了，不会出现"关闭后才 push、被丢弃"的情况。而 `pop` 只有在
"已关闭**且**队列为空"时才让 worker 退出，所以 worker 结束之前，队列里剩下的帧一定都被取走
了。再加上第 1 节的修复保证每帧像素都不会被改坏，校验都能通过，于是每一帧都会被处理并保存。

**输入耗尽时。** `next()` 返回 `false` 后，producer 调用 `close()`：

- **正在 `pop` 里等待的 worker** 会被 `notify_all` 唤醒。如果队列里还有帧，就继续取出处理；
  如果已经空了，`pop` 返回 `false`，worker 退出循环，线程函数结束。
- **正在处理某一帧的 worker** 不受影响，会把当前帧处理并保存完，然后回到循环再次 `pop`。
  这时队列要么还有剩余帧（继续处理），要么已空且已关闭（`pop` 返回 `false`，退出）。

## 3. 共享统计数据

指出哪些线程会读写 `Statistics`。解释原实现中的竞争为什么可能导致错误结果，并说明
你的同步方案提供了什么保证。还应说明取得快照时为什么是安全的。

**哪些线程会访问。** producer 线程写 `produced`；每个 worker 线程写 `processed`、`saved`
或 `corrupted`；main 线程（或测试）通过 `snapshot()` 读取全部计数。同一时刻可能有多个线程
在读写同一个对象。

**原实现为什么会出错。** `deliberatelySlowIncrement` 把加一拆成了三步："读出旧值 → 等待一
小段时间 → 写回旧值 + 1"，这三步不是一个整体。如果两个线程几乎同时进入，都读到了 5，
各自写回 6，结果本来应该加两次，却只加了一次，这就是"丢失更新"。中间那段 `sleep` 放大了
出错的时间窗口。`statistics_test` 让 8 个线程各加 50 次，正确结果是 400，原实现因为丢失更新
得到的数会偏少，测试因此失败。这是第三讲里说的**数据竞争**（多个线程同时访问同一份数据），和生命周期问题是两类
不同的问题。

**同步方案和保证。** 给 `Statistics` 加了一个 `std::mutex mutex_`，每个 `onXxx()` 开头都用
`std::lock_guard` 加锁。这样"读、改、写"三步都在同一把锁的保护下完成，同一时刻只有一个线程
能修改计数，每一次加一都不会丢失。`lock_guard` 用的是 RAII：构造时加锁，离开函数作用域时
析构、自动解锁，不需要手动调用 `unlock()`。

**快照为什么安全。** `snapshot()` 也加同一把锁，然后一次性读出四个计数。因为读写用的是同一
把锁，读的时候不会有线程正在修改，所以既不会读到写了一半的值，四个数也来自同一时刻，不会是
"一部分是新的、一部分是旧的"的混合状态。`snapshot()` 是 `const` 成员函数，但加锁需要修改
`mutex` 的状态，所以 `mutex_` 声明为 `mutable`。返回的是 `StatisticsSnapshot` 的值拷贝，
调用者拿到之后就和内部状态无关了，不需要继续持有锁。

## 4. 线程关闭协议

分别描述以下两条路径中的事件顺序，并解释为什么不会发生 `std::terminate`、悬空访问
或永久等待：

1. 调用者执行 `start()` 后显式调用 `wait()`；
2. 调用者执行 `start()` 后不调用 `wait()`，直接让 `Pipeline` 析构。

如果你的实现允许某个生命周期方法被重复调用，也请说明其行为；如果不允许，请说明前置条件。

**路径 1：`start()` 后调用 `wait()`。**

1. `start()` 先创建所有 worker 线程，它们进入 `pop` 等待；再创建 producer 线程。
2. producer 依次读取全部帧并 `push` 进队列，读完后调用 `close()`。
3. worker 不断取帧处理。队列关闭且被取空后，每个 worker 的 `pop` 返回 `false`，线程函数结束。
4. `wait()` 先 `join` producer（它在 `close()` 之后就结束了），再依次 `join` 每个 worker
   （它们在取空队列后结束）。`wait()` 返回时所有线程都已回收，不再可 join。
5. 之后 `Pipeline` 析构：producer 已经不可 join，所以析构函数会再调用一次 `close()`（重复
   关闭无害），然后调用 `wait()`，这时没有可 join 的线程，什么也不做。

**路径 2：`start()` 后直接析构。**

1. 析构函数体开始执行时，producer 和 worker 可能都还在运行。
2. producer 还可以 join，所以析构函数直接调用 `wait()`：先 `join` producer，等它读完剩下的帧
   并 `close()` 队列；再 `join` 每个 worker，等它们处理完剩余的帧并退出。
3. 只有所有 `join` 都返回之后，析构函数体才结束，接下来才会销毁 `queue_`、`statistics_`、
   `source_` 等成员。

**为什么不会出问题：**

- **不会 `std::terminate`**：销毁一个仍可 join 的 `std::thread` 会调用 `std::terminate`。
  两条路径里，每个线程对象在销毁之前都已经被 `join` 过了。
- **不会悬空访问**：线程函数通过捕获的 `this` 使用 `queue_`、`statistics_`、`processor_`、
  `source_` 等成员。C++ 的成员是在析构函数体执行**完之后**才销毁的，而我们在析构函数体里就
  已经等所有线程结束了，所以线程运行期间这些成员一直有效。
- **不会永久等待**：图像源是有限的，producer 最终一定会读完并调用 `close()`；`close()` 用
  `notify_all` 唤醒所有等待的 worker，它们取空队列后一定会退出，所以 `join` 一定能返回。

还有两种特殊情况：如果从未调用 `start()`，就没有任何线程，析构时 `close()` 和 `wait()` 都是
空操作。如果 `start()` 中途失败、producer 没有启动，就没人会关闭队列，等待中的 worker 会永远
卡在 `pop` 里，所以析构函数在 producer 不可 join 时会先补一次 `close()`，把这些 worker 唤醒。

路径 2 的代价是析构会阻塞，直到剩余的帧全部处理完才返回。对这个有限长的图像序列来说，这样
可以保证"安全关闭"和"已产生的帧都被处理"同时成立。

**重复调用的行为和前置条件：**

- `wait()` **可以重复调用**：每次只 `join` 仍可 join 的线程，第二次及以后调用什么也不做。
  先 `wait()` 再析构也是安全的。
- `close()` 可以重复调用：只是设置标志并唤醒等待者，没有副作用。
- `start()` **只能调用一次**，这是前置条件。再次调用会抛出 `std::logic_error`。否则会给仍可
  join 的 `producer_` 重新赋值（直接触发 `std::terminate`），或者让两批线程同时消费同一个
  队列。即使第一次运行已经 `wait()` 完毕也不能重新启动，因为队列已经关闭、图像源也已经读完。
- `statistics()` 可以在任何时候、从任何线程调用，因为 `snapshot()` 内部加了锁。
- 前置条件：`wait()` 和析构由创建 `Pipeline` 的线程（main 线程）负责调用，不要让多个线程同时
  对同一个 `Pipeline` 调用 `wait()`。
